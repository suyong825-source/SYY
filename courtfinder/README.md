# courtfinder — 서울시 공공 테니스장 날짜별 조회

서울시 공공서비스예약(yeyak.seoul.go.kr)의 테니스장 접수 건을 모아,
**날짜를 고르면 그날 예약 가능한 코트가 한눈에 보이는** 단독 HTML 파일을 만듭니다.

원본 사이트는 코트·기간 단위로 접수 건이 흩어져 있고(테니스장만 350건 이상, 6건씩 60페이지),
날짜로 가로질러 보는 화면이 없습니다. 이 도구는 그 목록을 날짜 축으로 뒤집습니다.

## 사용법

```bash
pip install -e .

courtfinder                    # 수집 후 tennis.html 생성
courtfinder -o ~/tennis.html   # 출력 경로 지정
courtfinder --offline          # 재수집 없이 기존 courts.json으로 HTML만 다시 생성
courtfinder --max-pages 3      # 앞 3페이지만 (동작 확인용)
courtfinder --delay 2          # 요청 간격 2초
```

만들어진 `tennis.html`은 외부 의존성이 없는 단일 파일입니다. 브라우저로 열면 됩니다.

## 화면

- **날짜 띠** — 각 날짜 밑 숫자가 그날 접수중인 건수. 숫자가 있는 날만 고르면 됩니다
- **필터** — 지역(구), 장소, 접수중만, 주간(07–17시) / 야간(17시 이후)
- **결과** — 장소별로 묶어 시간대순 정렬, 각 건마다 공식 예약 페이지 딥링크

## 무엇을 보여주고, 무엇을 보여주지 않는가

보여주는 것: 고른 날짜가 **이용기간에 포함되고 요일 조건이 맞는** 접수 건.

요일 조건에는 **공휴일**이 반영됩니다. 평일이지만 공휴일인 날(예: 2026-09-25 추석, 금요일)에는
평일 접수 건 대신 **주말·공휴일 접수 건**을 보여줍니다. 평일 건도 확인하려면
`공휴일에 평일 건도 보기` 버튼을 누르세요. 공휴일 표는 `holidays.py`에 있고,
음력 공휴일과 대체공휴일은 매년 관보로 확정되므로 연말에 한 번씩 확인하는 게 안전합니다.

보여주지 않는 것: **실시간 잔여석**. 서울시 사이트는 목록 페이지에 "10월 3일 14시 2자리 남음" 같은
정보를 싣지 않습니다. 잔여석은 각 서비스의 예약 달력에만 있고, 그 달력 API는
사이트가 자동 요청 차단(dynaPath)을 걸어둔 엔드포인트입니다 — 이 도구는 거기에 접근하지 않습니다.
따라서 최종 확인은 **예약하기** 링크를 눌러 공식 페이지에서 하세요.

## 수집 범위와 예의

- 공개된 검색 결과 페이지(`selectPageListDetailSearchImg.do`)만 GET으로 읽습니다
- 요청 사이에 기본 1초 간격을 둡니다
- 연결이 끊긴 페이지는 최대 4회까지 간격을 늘려가며 재시도합니다.
  그래도 실패하면 **몇 페이지가 빠졌는지 출력합니다** — 조용히 넘어가지 않습니다
- 로그인, 예약 신청, 봇 차단 우회는 하지 않습니다
- `robots.txt`는 이 경로를 Googlebot에만 막고 있고, 일반 요청에는 열려 있습니다
  (2026-09 기준). 개인 조회 용도로만 쓰세요

## 구조

| 파일 | 역할 |
|---|---|
| `parser.py` | HTML → `Service` 파싱. 네트워크를 타지 않는 순수 함수 |
| `holidays.py` | 대한민국 공휴일 표 (직접 고칠 수 있음) |
| `fetch.py` | 목록 페이지 순회 수집 |
| `render.py` | 수집 결과를 템플릿에 주입 |
| `template.html` | 생성되는 페이지의 본체 (JS/CSS 인라인) |
| `cli.py` | 커맨드라인 |

파싱 로직이 순수 함수로 분리돼 있어 네트워크 없이 테스트됩니다: `pytest`


## 접수 개방 시각 추적과 알람

목록 페이지에는 접수기간이 **날짜까지만** 나옵니다. 정확한 **시각**은 각 서비스의
상세 페이지에만 있어서(`접수기간 2026.09.25 07:00 ~`), 상세를 한 번 읽어야 합니다.

```bash
courtfinder --details --upcoming     # 시각 수집 + 코트별 다음 개방/알람 시각 출력
courtfinder --details --upcoming --minutes 15   # 알람을 15분 전으로
```

### 관찰 기록으로 패턴을 배운다

`--details`로 읽은 접수 건은 `history.jsonl`에 **처음 본 것만** 한 줄씩 쌓입니다.
이 기록이 쌓이면 코트별 개방 패턴(며칠, 몇 시, 월 단위인지 반달 단위인지)을
추론할 수 있고, 그때부터는 서버를 계속 두드리지 않고도 다음 회차를 예측합니다.

두 번째 실행부터는 **이미 아는 건의 시각을 기록에서 재사용**하므로,
새로 올라온 공고에 대해서만 상세를 읽습니다. 하루치 요청은 목록 59회 +
신규 건수 정도입니다.

`--upcoming` 출력의 `근거` 열:

| 값 | 뜻 |
|---|---|
| 확정 | 사이트에 이미 올라온 접수 건의 실제 개방 시각 |
| 추정 | 과거 회차 패턴으로 계산한 예측치 — 실제와 다를 수 있음 |

`회차` 열은 그 코트에서 서로 다른 개방 시점을 몇 번 관찰했는지입니다.
1이면 주기를 아직 검증하지 못한 상태라 추정을 믿기 이릅니다.
